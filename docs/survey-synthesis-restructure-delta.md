# Survey Synthesis Restructure Delta: v3.1 to v7.0 Conformance

**Date:** 2026-05-20
**Status:** Proposed (awaiting approval before implementation)
**Reference:** `desk_research.yaml` v7.0, `stakeholder_synthesis.yaml` v7.0, ADR 0005/0016

---

## 1. Current state of survey synthesis

The survey synthesis template (v3.1) uses the **same "single LLM" pattern** as stakeholder synthesis pre-restructure. The output template is:

```handlebars
{{ai_generated.survey_synthesis_complete}}
```

One task generates the entire document — masthead, overview table, theme summary table, per-theme sections, sentiment overview, recommendations, methodology, references, and footer.

### Architecture

One AI task: `survey_synthesis_complete` (~220 lines of prompt). The prompt contains the complete document skeleton with placeholder values. Same pattern as stakeholder_synthesis v5.0 — the LLM owns everything.

### What the LLM controls that it shouldn't

| Value | Current | Should be |
|-------|---------|-----------|
| Document title and masthead | LLM generates `# Survey Synthesis: {{survey_name}}` | Handlebars: `{{survey_name}}` |
| Overview table (survey name, response count, etc.) | LLM fills table slots | Handlebars for known values (survey_name, question_focus); LLM for computed values (response count, theme count, top finding) |
| Methodology section | LLM generates boilerplate | Handlebars: static text |
| References list | LLM generates fixed list | Handlebars: static list |
| Footer (`Generated by Qori`) | LLM generates | Already handled by yamlProcessor's `buildTraceabilityFooter` — the LLM prompt explicitly includes a footer that duplicates the auto-generated one |

### Handler path

Routes through `discoverHandler.ts`. The `DiscoveryTemplateInput` already includes `topic`, `effective_topic`, `topic_slug`, `document_count`, `document_names`, `document_types` from earlier fixes. Survey-specific fields added at lines 349-353:
- `survey_name`
- `question_focus`
- `survey_files`

### topic_slug bug

**Same status as the other two discovery templates.** The YAML declares `derived_variables: topic_slug: "{{topic | slugify}}"` (line 390) but `derived_variables` is never processed. `discoverHandler.ts` now computes `topic_slug` in the data object — so filename and discovery scoping work correctly. The `derived_variables` block should be removed.

### Anti-fabrication guards

**Present but less rigorous than desk research or stakeholder synthesis.** Five rules in the prompt:
1. Theme-by-theme aggregation (not response-by-response)
2. Every theme needs frequency + quotes
3. Respondent citation format (R001, R002)
4. Sentiment with meaning (explain what drives it)
5. No hallucination — only report themes from data, counts must be accurate, quotes verbatim

Missing compared to desk research: no empty-content detection, no OUTPUT BOUNDARIES rule.

### Cascade summary section

**Missing.** No cascade summary documenting what the template emits.

### What it emits

Seven cascade variables, all with `pool: true` / `pool_strategy: append` (except `sample_demographics`):

| Variable | Schema | Downstream consumers |
|----------|--------|---------------------|
| `survey_themes` | `$ref: schemas/survey_theme.yaml` | `research_brief` (manual load) |
| `survey_findings` | `$ref: schemas/survey_finding.yaml` | `research_brief` (manual load) |
| `survey_recommendations` | `$ref: schemas/survey_recommendation.yaml` | Not consumed by any template (orphaned) |
| `discovered_barriers` | `$ref: schemas/discovered_barrier.yaml` | `research_brief` (manual load), `stakeholder_synthesis` (formal consumes) |
| `discovered_metrics` | `$ref: schemas/discovered_metric.yaml` | `research_brief` (manual load) |
| `sample_demographics` | inline schema (object, not array) | Not consumed by any template (orphaned) |
| `knowledge_gaps` | inline schema (object array) | `research_brief` (manual load), `stakeholder_synthesis` (formal consumes) |

Two orphaned variables: `survey_recommendations` and `sample_demographics`. These are emitted but never consumed downstream. Matches the v1.1 followup finding about orphaned cascade variables.

### Duplicate footer

The prompt template includes `*Generated by Qori • {{current_date}}*` at line 290. yamlProcessor's `buildTraceabilityFooter` already appends a traceability footer to every document. This creates a duplicate: LLM-generated footer + auto-generated footer. The v7.0 restructure should remove the LLM-generated footer (desk research and stakeholder synthesis both removed theirs).

### What's missing vs. v7.0

| v7.0 feature | Status |
|--------------|--------|
| Interleaved Handlebars + bounded LLM slots | No — single LLM blob |
| Computed values rendered mechanically | No — everything through LLM |
| Anti-fabrication guards | Present but incomplete (no empty detection, no OUTPUT BOUNDARIES) |
| Cascade summary | Missing |
| Handler assembles mechanical data | Partially — document count/names/types available but not survey_name metadata |

## 2. Target state

Follow the same pattern as desk research v7.0: Handlebars for structure, bounded LLM tasks for analytical content. Survey synthesis is structurally similar to desk research — it analyzes uploaded data and produces a synthesis.

### Task split

Unlike stakeholder synthesis (which needed cross-section coherence), survey synthesis sections are largely independent. The theme analysis is the core; everything else derives from it. Recommended split:

1. **analysis_body** — Theme summary table + per-theme sections + sentiment overview (one task to preserve theme numbering consistency)
2. **Handlebars** — Masthead, overview table (partial: survey_name and question_focus mechanical, response/theme counts from LLM), methodology, references, cascade summary

The recommendations section follows the desk research pattern: rename to "Knowledge Gaps" or remove entirely. Survey recommendations have the same issue as desk research — the LLM suggests product actions that belong in the brief.

**Recommendation:** Apply the same treatment as desk research — rename to "Knowledge Gaps" and narrow to what the survey data couldn't answer. The `survey_recommendations` variable is orphaned anyway (no downstream consumer), so removing recommendations doesn't break cascade.

## 3. Specific changes required

### 3a. YAML changes (`survey_synthesis.yaml`)

**Split into 1 AI task + Handlebars structure:**

1. `analysis_body` — Theme summary table, per-theme sections (frequency, sentiment, quotes, pattern), sentiment overview. One task preserves theme numbering.

**Handlebars renders:**
- Masthead: `# Survey Synthesis: {{survey_name}}`
- Overview table: survey_name, question_focus mechanical; note that response count and theme count come from the AI task output (not handler-computable — the LLM counts responses from uploaded CSV data)
- Methodology boilerplate (in `<details>` toggle, matching desk research pattern)
- References (static, in `<details>` toggle)
- Cascade summary (always present)

**Remove:**
- Recommendations section → replace with Knowledge Gaps (same as desk research)
- LLM-generated footer (duplicate of yamlProcessor's auto-footer)
- `derived_variables` block

**Add:**
- Anti-fabrication: empty-content detection, OUTPUT BOUNDARIES rule
- Cascade summary section listing all 7 emitted variables

### 3b. Handler changes

None needed beyond what's already in `discoverHandler.ts`. Survey-specific fields (`survey_name`, `question_focus`, `survey_files`) are already passed. `topic_slug` is already computed.

### 3c. Cascade contract changes

**No shape changes.** All 7 emit schemas stay the same. The `survey_recommendations` variable becomes less useful (knowledge gaps instead of product actions) but the schema shape doesn't change — the extractor still extracts from whatever section exists.

**Consider:** Remove `survey_recommendations` emit entirely since it's orphaned. But this is a separate decision from the restructure — file as v1.1 followup if not ready to remove.

## 4. Cascade contract impact

### Downstream consumers

`research_brief` consumes `survey_themes` and `survey_findings` via manual loading. These are used in the brief's problem_narrative, summary, and method_rationale prose tasks. No changes needed — the variable shapes are unchanged.

### Extraction impact

Positive. Section headings rendered mechanically (Handlebars) means consistent heading names for `extract_from` hints. Currently the LLM occasionally varies theme heading format.

## 5. Risks

### Risk 1: Response count and theme count not handler-computable

Unlike desk research (where document count comes from `processedFiles.length`), survey response count requires parsing the uploaded CSV data. The handler doesn't parse CSVs — it passes raw content to the LLM. So `response_count` and `theme_count` can't be pre-computed by the handler. They remain in the LLM output.

**Mitigation:** Accept this. The overview table will have a mix: `survey_name` and `question_focus` rendered mechanically, `response_count` and `theme_count` as part of the AI-generated overview.

### Risk 2: Smallest of the three discovery restructures — may feel perfunctory

Survey synthesis is the simplest discovery template. The restructure is smaller than stakeholder (which had Mermaid diagrams, confidence rubrics, 7 numbered sections) and comparable to desk research. The core work is the same: extract static content to Handlebars, add OUTPUT BOUNDARIES, add cascade summary.

**Mitigation:** Don't inflate scope. The template is genuinely simpler.

## 6. Implementation sequence

1. Handlebars skeleton (masthead, methodology toggle, references toggle, cascade summary)
2. Split AI task (single `analysis_body` task replacing `survey_synthesis_complete`)
3. Rename Recommendations to Knowledge Gaps
4. Add anti-fabrication improvements (empty detection, OUTPUT BOUNDARIES)
5. Remove `derived_variables`, duplicate footer
6. Verify extraction produces same 7 variable types

**Estimated effort:** 1 session (smallest of the three discovery restructures).
