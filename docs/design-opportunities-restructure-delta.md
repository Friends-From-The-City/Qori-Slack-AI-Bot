## 1. Current state of design_opportunity_generator

### Architecture

Single-LLM blob. One task `opportunities_complete` (~190 lines of prompt) generates the entire document including title, masthead, methodology, references, and footer. Output template: `{{ai_generated.opportunities_complete}}`. Handler routes through `researchSynthesisHandler.ts` via `ANALYSIS_YAML_MAPPING['design_opportunities'] = 'design_opportunity_generator.yaml'`. Listed in `NUGGET_REQUIRED_METHODS`.

### Cascade contract -- consumes

| Variable | Source | Required | inject_as |
|----------|--------|----------|-----------|
| `atomic_nuggets` | session_summary | Yes | context |
| `validated_themes` | affinity_mapping | No | context |
| `personas` | persona_generator | No | context |
| `stakeholder_constraints` | stakeholder_synthesis | No | context |
| `validated_jobs` | jobs_to_be_done | No | reference |

5 upstream variables (the richest consume set of any lateral analysis template). Note: `validated_jobs` was just wired in the JTBD PR #150 — pending merge. Generic `atomic_nuggets` key and `inject_as: context` pattern need updating.

### Cascade contract -- emits

**None.** The template generates rich structured HMW opportunities (problem statement with quote, HMW formula with verb/user/situation/outcome, impact assessment, design direction, scope/priority, prioritization matrix) but declares no `emits:` section. Last cascade dead-end.

### Downstream consumers expecting output

**None declared.** No template references design_opportunities output. Unlike usability_issues (research_readout expected it) or JTBD (we wired design_opportunities as consumer), this template's output currently goes nowhere in the cascade.

**Potential consumers:**
- `designer_readout` — already generates design_ticket_candidates from prioritized_findings. HMW opportunities could enrich ticket descriptions with opportunity framing. But designer_readout works through research_readout's findings, not directly from synthesis-layer data.
- `github_issues_generator` — converts readout tickets into GitHub issues. Could reference HMW statements as context. But same indirect path applies.

**Decision: No downstream wiring in this pass.** This template is the last lateral analysis template. Its value is the generated document itself (researchers read it), not cascade variable propagation. Adding an emit schema still has value for potential future consumption and for structural completeness, but no template needs to be wired as a consumer right now.

### What the LLM generates that should be mechanical

| Element | Current | Should be |
|---------|---------|-----------|
| Document title + summary stat line | LLM generates `# 💡 Design Opportunities: {{selected_study}}` | Handlebars |
| Overview table | LLM generates | Keep in LLM -- analytical synthesis |
| Per-opportunity sections (problem, HMW, impact, design direction, scope/priority) | LLM generates | Keep in LLM -- core analysis |
| Prioritization matrix | LLM generates | Keep in LLM -- analytical |
| Methodology + references | LLM generates static content + references | **Split:** Handlebars renders references (static), LLM writes data sources |
| Footer (`*Generated by Qori*`) | LLM generates | Handlebars (backend footer handles this) |
| Cascade summary | **Missing** | Handlebars (standard v7.0) |
| Upstream context | **Missing** | Handlebars (conditional on upstream vars) |
| Validity checklist | **Missing** | Handlebars (static) |

### Anti-fabrication guards

**Strong — 7 rules** (the most of any lateral analysis template):

1. HMWs COME FROM PROBLEMS -- no invention, must cite participant + quote
2. HMW FORMULA -- verb/user/situation/outcome structure
3. SCOPE -- not too broad, not too narrow (with examples)
4. NO SOLUTIONS IN HMWs -- invite exploration, don't prescribe
5. VA CONTEXT ONLY -- domain-scoped with explicit exclusion list
6. CITE EVERYTHING -- participant ID + quote + timestamp
7. VERIFY BEFORE SUBMITTING -- quality checklist

These are well-suited to HMW framing. Preserved as-is.

### Dead metadata sections

`processing_workflow`, `auto_variables`, `notify`, `quality_assurance` -- documentation-only. Safe to remove.

## 2. Emit schema design: design_hmw_opportunity

### Design rationale

No template currently consumes this output, but an emit schema serves two purposes:
1. **Structural completeness** -- every v7.0 synthesis template should declare what it produces
2. **Future consumption** -- designer_readout or a future "opportunity backlog" template could consume pre-structured HMW opportunities

The schema should capture the HMW formula structure (verb/user/situation/outcome) plus evidence links, impact assessment, and design direction.

### Comparable schemas

| Schema | Purpose | Required fields | Nullable fields | Total |
|--------|---------|:-:|:-:|:-:|
| `prioritized_issue` | Severity-rated problem | 7 | 10 | 17 |
| `validated_job` | Progress-focused need | 7 | 10 | 17 |
| `design_ticket_candidate` | Actionable design work | 6 | 8 | 14 |

`design_hmw_opportunity` should be leaner than issues/jobs since HMWs are intentionally open-ended. The required core captures the HMW statement + evidence link; enrichment adds impact and design direction.

### Proposed schema: `design_hmw_opportunity.yaml`

```yaml
type: object
required: [id, hmw_title, hmw_statement, source_problem, evidence_nuggets, confidence]
properties:
  # -- Required core (6 fields) --
  id:
    type: string
    description: "Format: hmw-01, hmw-02, etc."
  hmw_title:
    type: string
    description: "Short descriptive name for the opportunity"
  hmw_statement:
    type: string
    description: "Full HMW: 'How might we [verb] for [user] when [situation] so that [outcome]?'"
  source_problem:
    type: string
    description: "1-2 sentence problem statement grounded in research quote"
  evidence_nuggets:
    type: array
    items:
      type: string
    description: "References to atomic_nugget_core.id values"
  confidence:
    type: string
    enum: [Strong, Moderate, Limited]
    description: "Evidence quality assessment"

  # -- Enrichment (9 nullable fields) --
  participants_affected:
    type: array
    nullable: true
    items:
      type: string
    description: "PT-XXX IDs whose data supports this opportunity"
  participant_coverage:
    type: string
    nullable: true
    description: "X of Y participants format"
  impact:
    type: string
    nullable: true
    enum: [High, Medium, Low]
    description: "User impact if problem remains unsolved"
  effort:
    type: string
    nullable: true
    enum: [High, Medium, Low]
    description: "Implementation effort estimate"
  design_direction:
    type: string
    nullable: true
    description: "General approach — NOT a specific solution"
  success_metric:
    type: string
    nullable: true
    description: "Measurable outcome (e.g., 'finds feature in under 2 taps')"
  linked_themes:
    type: array
    nullable: true
    items:
      type: string
    description: "validated_theme.id references"
  linked_jobs:
    type: array
    nullable: true
    items:
      type: string
    description: "validated_job.id references if opportunity addresses a job"
  linked_barriers:
    type: array
    nullable: true
    items:
      type: string
    description: "target_barrier IDs (TB-XXX)"
```

**Total: 6 required + 9 nullable = 15 fields.** Extraction model: Sonnet (HMW synthesis + evidence linking). Replace strategy (study-level).

Slightly leaner than issues/jobs (6 required vs 7) because HMWs are intentionally open-ended -- the `hmw_statement` is one field, not a split triad like jobs.

## 6. Risks

### Risk 1: First-time extraction

Same as usability_issues and JTBD. 6 required + 9 nullable fields across ~3-6 opportunities per study. Moderate complexity.

**Mitigation:** Sonnet extraction. Prompt already generates structured per-opportunity sections with HMW formula, impact, and design direction.

### Risk 2: No downstream consumer to verify flow

The emit exists for completeness. No consumer tests the extracted data in a downstream template.

**Mitigation:** Verify extraction produces valid JSON with correct field shapes. If a consumer is needed later, the schema and extraction are ready.

### Risk 3: validated_jobs consume depends on PR #150

The `validated_jobs` consume was added in the JTBD PR. If that PR isn't merged when this PR lands, the consume declaration references a variable that doesn't exist yet (graceful degradation -- it's optional).

**Mitigation:** Merge PR #150 first, or accept that the consume works correctly with or without the upstream data.
