# Desk Research Structural Changes Delta

**Date:** 2026-05-19
**Status:** Proposed (awaiting approval before implementation)
**Prerequisite:** Desk research v7.0 bugs resolved (effective_topic, document_count, dual handler fix)

---

## Current state

The desk research v7.0 template renders sections in this order:

1. **Masthead** — title, study, date
2. **Research Overview** — metadata table (study, topic, date, document count, analysis type), document context, anti-hallucination note
3. **Documents Analyzed** — mechanical file list table + AI per-document analysis (source, date, type, relevance, summary)
4. **Executive Summary** — overview, 5 key findings with blockquotes, strategic implications, confidence assessment table
5. **Key Themes** — 3-5 themes with evidence quotes, implications, confidence rating
6. **Recommendations** — immediate actions table, short-term priorities table, further research needed table
7. **References** — source table + per-document `<details>` blocks
8. **Methodology Note** — 4-row practice/implementation table
9. **Cascade summary** — emitted variables table, document count
10. **Document Information** — traceability footer (auto-generated by yamlProcessor)

---

## Question 1: Recommendations section

### Analysis

The Recommendations section currently generates three sub-sections:
- **Immediate Actions (This Week)** — specific product/engineering actions
- **Short-Term Priorities (This Month)** — larger product changes
- **Further Research Needed** — gaps and suggested methods

The first two are forward-looking product actions ("Add next appointment widget to home screen", "Redesign Benefits section"). These are the LLM's most extrapolation-prone output — the anti-fabrication guards say "EVERY recommendation must trace directly to a finding" but the LLM still generates specific implementation suggestions (rename buttons, add widgets) that go beyond what the source documents recommend.

The third sub-section ("Further Research Needed") IS appropriate for desk research — it documents what the literature couldn't answer and suggests investigation methods. This is where `methodology_recommendations` and `knowledge_gaps` cascade variables are extracted from.

### Recommendation: Option B — rename and narrow

Remove "Immediate Actions" and "Short-Term Priorities" tables. Keep "Further Research Needed" and rename the section to **"Knowledge Gaps and Research Implications"**. This section covers:
- What the literature couldn't answer (knowledge gaps)
- What research methods the findings suggest (methodology recommendations)

This preserves both cascade variables (`methodology_recommendations`, `knowledge_gaps`) that downstream consumers depend on, while eliminating the product-action recommendations that belong in the brief.

### Cascade impact

- `methodology_recommendations` — **preserved.** Extract_from hint changes from "Recommendations section, Further Research Needed" to "Knowledge Gaps and Research Implications section". Same data, different section name.
- `knowledge_gaps` — **preserved.** Same change to extract_from hint.
- `research_brief` consumes `methodology_recommendations` in the method_rationale prompt ("N discovery sources independently recommended..."). **No change needed** — the variable shape is unchanged.

### Changes required

**YAML:**
- Rename `recommendations` task to `knowledge_gaps_prose`
- Rewrite prompt to focus on gaps and research implications only (no product actions)
- Update extract_from hints for `methodology_recommendations` and `knowledge_gaps` to reference new section name
- Rename section heading in output template from "Recommendations" to "Knowledge Gaps and Research Implications"

**Handler:** No change.

## Question 2: Documents Analyzed at the top

### Analysis

The reader's first question is "what did you read?" Currently they see a metadata table (Research Overview) before the document list. The metadata table duplicates information already in the masthead (study, date) and adds low-value fields (analysis type is always "Secondary Research / Literature Review").

### Recommendation: Merge Research Overview into masthead, move Documents Analyzed to first section

The masthead already shows study and date. Add document count and topic to the masthead. Remove the Research Overview section entirely — its metadata is redundant or low-value. The anti-hallucination note moves to a context block under the masthead. Documents Analyzed becomes the first body section.

### New section order

1. **Masthead** — title, study, topic, date, document count, anti-hallucination note
2. **Documents Analyzed** — mechanical file list + AI analysis
3. **Executive Summary**
4. **Key Themes**
5. **Knowledge Gaps and Research Implications** (renamed from Recommendations)
6. **References**
7. **Methodology Note** (in `<details>` toggle)
8. **Cascade summary**
9. **Document Information** (traceability footer)

### Cascade impact

None. Section reordering doesn't affect variable extraction — the extractor uses section headings from extract_from hints, not positional order.

### Changes required

**YAML output template only.** Merge masthead metadata, remove Research Overview section, reorder sections.

## Question 3: `<details>`/`<summary>` toggles

### Candidates evaluated

| Content | Current rendering | Toggle? | Rationale |
|---------|------------------|---------|-----------|
| **Confidence Assessment** (in Executive Summary) | Visible table | **Yes** | Metadata about the analysis, not a headline finding. Researchers scan findings first, check confidence second. |
| **Methodology Note** | Visible table | **Yes** | Boilerplate — identical every time. Useful for audit but not for first read. |
| **Per-document analysis** (in Documents Analyzed) | Visible paragraphs | **Yes** | The file list table is scannable; per-document detail (source, date, relevance, summary) expands on demand. |
| **Cascade summary** | Visible table | **No** | Patent-defensibility artifact. Must stay visible for provenance documentation. |
| **References source table** | Visible table | **No** | Already scannable. Per-document details already use toggles (working well). |
| **Key Themes evidence quotes** | Visible blockquotes | **No** | Core analytical content. Evidence is what makes themes credible. |

### Recommendation: Toggle confidence assessment, methodology note, per-document analysis

Three toggles. Each wraps content that's valuable for audit but not for first-pass reading:

```markdown
<details>
<summary><strong>Confidence Assessment</strong></summary>
[table]
</details>
```

```markdown
<details>
<summary><strong>Methodology Note</strong></summary>
[table]
</details>
```

Per-document analysis is trickier — each document gets its own toggle under the mechanical file list:

```markdown
| # | Filename | Type |
|:-:|:---------|:-----|
| 1 | report.pdf | PDF |
| 2 | analysis.md | Markdown |

<details>
<summary><strong>1. report.pdf</strong> — VA Digital Analytics Team, January 2026</summary>
[AI analysis paragraph]
</details>

<details>
<summary><strong>2. analysis.md</strong> — VA Office of the CTO, March 2026</summary>
[AI analysis paragraph]
</details>
```

This requires the `document_analysis` AI task to output per-document blocks that can be wrapped. Currently it outputs a continuous stream of per-document sections separated by `---`. The task prompt would need to output a structured format that the template can iterate and wrap.

**Alternative for per-document analysis:** Keep the current single `{{ai_generated.document_analysis}}` block but wrap the entire thing in one toggle:

```markdown
<details>
<summary><strong>Document details</strong> — source, relevance, and summaries</summary>
{{ai_generated.document_analysis}}
</details>
```

Simpler, no prompt restructuring needed. Individual document details are less important than the aggregate — the file list table gives the scan, the toggle gives the depth.

**Recommendation:** Single toggle for document analysis (simpler), individual toggles deferred to a later pass if researchers want per-document expansion.

### Cascade impact

None. Toggles are rendering changes. The rendered markdown still contains the same text for extraction.

### Changes required

**YAML output template only.** Wrap three sections in `<details>`/`<summary>` tags.

## Refinement 1: MIME type to friendly labels

### Current

`processedFiles` returns `file.mimetype` as the type (e.g., `text/plain`, `application/pdf`). The Handlebars template renders it raw.

### Fix

Map in the handler before passing to the template:

```typescript
const MIME_LABELS: Record<string, string> = {
  'application/pdf': 'PDF',
  'text/plain': 'Text',
  'text/markdown': 'Markdown',
  'application/vnd.openxmlformats-officedocument.wordprocessingml.document': 'Word',
  'application/msword': 'Word',
};

const documentTypes = processedFiles.map((f) => MIME_LABELS[f.type] || f.type);
```

### Changes required

**Handler only** (`discoverHandler.ts` and `deskResearchHandler.ts`). YAML template unchanged — it already renders `{{lookup ../document_types @index}}`.

## Risks

### Risk 1: Removing product recommendations may disappoint researchers expecting actionable output

The "Immediate Actions" and "Short-Term Priorities" tables are the most visually actionable part of the current output. Removing them makes desk research purely analytical.

**Mitigation:** The brief is where actions live. Desk research informs; brief decides. Researchers who want immediate actions should run `/qori-brief` after desk research. The knowledge gaps section still provides forward-looking direction.

### Risk 2: Per-document toggle may affect variable extraction

If per-document analysis is inside `<details>` tags, the variable extractor still sees the text (HTML tags don't affect extraction). But if the toggle changes the section heading pattern that `extract_from` relies on, extraction could break.

**Mitigation:** Test extraction after adding toggles. The `extract_from` hints reference section names ("Executive Summary", "Key Themes") which remain visible outside toggles. Per-document detail is not directly referenced by any extract_from hint.

## Recommended implementation sequence

1. **Refinements first** (lowest risk, immediate quality improvement):
   - MIME type labels in handler
   - Theme implications phrasing in prompt

2. **Section reorder** (medium risk, no prompt changes):
   - Merge Research Overview into masthead
   - Move Documents Analyzed to first section

3. **Recommendations rename** (medium risk, prompt + extract_from changes):
   - Rename to "Knowledge Gaps and Research Implications"
   - Narrow prompt to gaps and methods only
   - Update extract_from hints

4. **Toggles last** (lowest priority, rendering-only):
   - Confidence assessment toggle
   - Methodology note toggle
   - Document analysis toggle

Each step can be verified independently. Steps 1-2 have no cascade impact. Step 3 requires extraction verification. Step 4 requires extraction verification for the document analysis toggle.
