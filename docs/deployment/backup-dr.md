# Backup and Disaster Recovery Contract

Backup infrastructure is **external to Qori**. The operating organization is responsible for database backup and recovery appropriate to its deployment environment.

## Current Production Implementation

The current Friends Innovation Lab deployment uses:

- **Railway-managed PostgreSQL** — infrastructure-level PITR via WAL archiving
- **Scheduled logical backup** — `pg_dump` to S3-compatible storage
- **Restore validation** — `scripts/validate-restore.js` verifies restored database integrity

This is a deployment choice, not an architectural requirement.

## Provider-Neutral DR Contract

Any Qori deployment must have:

### 1. Infrastructure-Level Recovery

The PostgreSQL instance must have recovery capability appropriate to the deployment's RPO/RTO requirements:

- **PITR (recommended)** — WAL archiving to durable storage for point-in-time recovery
- **Managed snapshots** — if using a managed database service
- **Filesystem snapshots** — if running on infrastructure that supports them

### 2. Scheduled Logical Backup

Periodic `pg_dump` exports to a storage destination independent of the database host:

- Any S3-compatible object storage (AWS S3, MinIO, Cloudflare R2, GCS with S3 interop)
- Any durable blob storage accessible via standard protocols
- Retention policy appropriate to organizational records requirements

### 3. Independent/Offsite Storage

Backup destination must be independent of the primary database infrastructure:
- Different availability zone, region, or provider
- Accessible if the primary infrastructure is unavailable
- Durability appropriate to data classification

### 4. Documented Restore Procedure

The operating organization must document and periodically test:

1. How to provision a new PostgreSQL instance
2. How to restore from logical backup (`pg_restore` or `psql < dump.sql`)
3. How to verify the restored database (run `scripts/validate-restore.js`)
4. How to point Qori at the restored database (update `DB_*` environment variables)
5. Expected RTO (recovery time objective)

### 5. Restore Validation

After any restore, run the schema validation:

```bash
cd backend
node scripts/validate-restore.js
```

This verifies:
- Migration state matches expected count
- Required tables exist
- Schema matches model definitions

## What Qori Does NOT Include

- No built-in backup scheduler (this is infrastructure)
- No backup storage client (S3 client, etc.)
- No automated failover
- No replication management
- No backup monitoring/alerting

These are infrastructure-level concerns owned by the operating organization.

## Application-Level Data Safety

Qori does protect data at the application level:

- **Transactions** for multi-row operations (variable store writes)
- **Idempotent external actions** (ADR 0036) to prevent duplicate side effects on retry
- **Fail-closed** startup if migration state is inconsistent
- **No destructive operations** without explicit admin action and confirmation

## Redis Recovery

Redis data loss has no impact. See [redis.md](./redis.md). No Redis backup is required.

## GitHub Recovery

GitHub is a projection store. If GitHub data is lost, it can be regenerated by re-running the relevant Qori workflows. The canonical data in PostgreSQL is unaffected. However, GitHub content may include manually-edited documents — the operating organization should consider GitHub's own backup capabilities for those.
