# Stakeholder Synthesis Restructure Delta: v5.0 to v7.0 Conformance

**Date:** 2026-05-20
**Status:** Proposed (awaiting approval before implementation)
**Reference:** `desk_research.yaml` v7.0 (most recent discovery template), ADR 0005/0016

---

## 1. Current state of stakeholder synthesis

The stakeholder synthesis template (v5.0) is the **purest "single LLM" pattern** in the codebase. The entire document — from masthead to appendix — is generated by one monolithic AI task (`synthesis_complete`). The output template is literally:

```handlebars
{{ai_generated.synthesis_complete}}
```

One line. The LLM generates the complete document including the masthead, all tables, all sections (01-07), methodology, appendix, and cascade summary. Every value — study name, researcher name, date, section headings, table structures — passes through the LLM.

### Architecture

One AI task: `synthesis_complete` (~440 lines of prompt). The prompt contains the full document skeleton inline, with placeholder values the LLM fills. This is the inverse of v7.0's pattern: instead of the template owning structure and the LLM filling bounded slots, the LLM owns everything.

### What the LLM controls that it shouldn't

| Value | Current | Should be |
|-------|---------|-----------|
| Masthead (study, researcher, date, status) | LLM generates from prompt template | Handlebars: `{{selected_study}}`, `{{researcher_contact}}`, `{{current_date}}` |
| Section headings (## 01, ## 02, etc.) | LLM generates | Handlebars: fixed section headings |
| Stakeholder count in summary table | LLM counts from input | Handler: count from `stakeholder_files.length` or parse from input |
| Methodology section framework text | LLM generates boilerplate | Handlebars: static text |
| Appendix structure (details/summary tags) | LLM generates HTML | Handlebars: static HTML structure |
| Validity checklist | LLM generates a fixed table | Handlebars: static table |
| References (hardcoded book list) | LLM generates | Handlebars: static reference list |
| Cascade summary table | LLM generates when upstream data exists | Handlebars: `{{#if upstream_discovered_barriers}}` |

### Handler path

Stakeholder synthesis routes through `discoverHandler.ts` (same as desk research). The `DiscoveryTemplateInput` data object already includes `topic`, `effective_topic`, `topic_slug`, `document_count`, `document_names`, `document_types` from our earlier fix. The stakeholder-specific fields added at line 356-360:
- `study_channel` = reply channel
- `researcher_contact` = `<@userId>` (Slack mention format)
- `detected_files` = joined filename list

### topic_slug bug

**Confirmed present in the same way as desk research was.** The YAML's `derived_variables` block declares `topic_slug: "{{topic | slugify}}"` (line 654) but `derived_variables` is never processed by yamlProcessor. However, `discoverHandler.ts` now computes `topic_slug` in the data object (from our earlier fix). So the filename and discovery scoping work correctly via the handler. The YAML `derived_variables` block is dead — same as desk research.

**Status: Already fixed by the discoverHandler.ts change.** The v7.0 restructure should remove the `derived_variables` block and add a comment noting that the handler computes these.

### Truncation issue

The v5.0 template consolidated from 4 AI tasks to 1 comprehensive task. The single task produces ~290 lines of output. With `max_tokens: 8192`, this approaches but doesn't exceed the budget for most interviews. The translation plan notes truncation risk is "Low" with the mitigation being Rule 5: "You MUST complete ALL sections including Methodology and Appendix."

The restructure reduces this risk by pulling static content (methodology boilerplate, validity checklist, references, appendix structure) out of the LLM's output budget and into Handlebars. This frees ~60-80 lines of token budget for analytical content.

### Anti-fabrication guards

**Present and thorough.** Six explicit rules in the prompt:
1. Role-only attribution (non-negotiable)
2. No hallucination — extractor, not generator
3. Confidence per section with stakeholder interpretation rubric
4. Maximum 2 sequence diagrams
5. Complete all sections
6. No metadata fabrication (interview durations, dates, metrics)

These are stronger than desk research's guards. The stakeholder synthesis is the most rigorously constrained template.

### Cascade summary section

**Partially present.** The cascade summary only renders when upstream `discovered_barriers` are available (conditional in the LLM prompt). When no upstream data exists, there's no cascade summary documenting what the template emits. The v7.0 version should always render a cascade summary — it emits 6 variables regardless of whether it consumed upstream data.

### What it emits

Six cascade variables:

| Variable | Schema | Downstream consumers |
|----------|--------|---------------------|
| `stakeholder_constraints` | `$ref: schemas/stakeholder_constraint.yaml` (10+ fields) | `research_brief`, `design_opportunities`, `service_blueprint`, `research_readout`, `engineering_readout` |
| `stakeholder_priorities` | `$ref: schemas/stakeholder_priority.yaml` | `research_brief` |
| `alignment_gaps` | `$ref: schemas/alignment_gap.yaml` | `research_brief`, `research_readout` |
| `stakeholder_questions_for_users` | `$ref: schemas/stakeholder_question.yaml` | `research_brief` (drives research question generation) |
| `backstage_observations` | inline schema | `service_blueprint` |
| `system_failure_modes` | inline schema | `service_blueprint` |

`stakeholder_constraints` and `stakeholder_questions_for_users` use `extraction_model: sonnet` (complex schemas with 10+ fields and priority enums).

### What's missing vs. v7.0

| v7.0 feature | Status |
|--------------|--------|
| Interleaved Handlebars + bounded LLM slots | No — single LLM blob |
| Computed values rendered mechanically | No — everything through LLM |
| Anti-fabrication guards | Present and strong |
| Cascade summary (always present) | Partial — only when upstream data exists |
| Handler assembles all mechanical data | Partially — discoverHandler passes topic, files, but no document inventory for the template |

## 2. Target state

Split the monolithic `synthesis_complete` task into:
- **Handlebars-rendered structure:** Masthead, section headings, methodology boilerplate, validity checklist, references, appendix HTML structure, cascade summary
- **Bounded AI tasks:** Each numbered section (01-07) plus the summary and appendix observations

This is the largest restructure so far — 7+ analytical sections, each needing its own bounded task. The desk research had 5 tasks; the brief had 7. Stakeholder synthesis needs ~10.

### Key design question: task count vs. monolithic

The v5.0 template consolidated from 4 to 1 task specifically to improve coherence — stakeholder synthesis needs cross-section references (SH-001 in constraints referenced again in priorities). Splitting back into per-section tasks risks losing this cross-referencing.

**Recommendation:** Split into 3 groups, not 7 individual tasks:
1. **stakeholder_table** — Stakeholder ID/role mapping table (mechanical + analytical)
2. **analysis_body** — Sections 01-05 as one analytical task (preserves cross-referencing of SH-XXX IDs, constraints → priorities → questions flow)
3. **appendix_observations** — Raw system/process observations for the appendix

Sections 06 (Open questions) and 07 (Recommendations) come from the analysis_body task. The methodology section, validity checklist, references, and HTML structure are all Handlebars.

This reduces the risk of losing cross-section coherence while still pulling mechanical content out of the LLM's budget.

## 3. Specific changes required

### 3a. Handler changes (`discoverHandler.ts`)

Stakeholder-specific data is already assembled (lines 356-360). Additional mechanical data to add:
- `stakeholder_count`: count of uploaded files (each file = one stakeholder interview)
- `file_list`: formatted list of interview files for the methodology section

```typescript
if (discoveryType === 'stakeholder_synthesis') {
  data.study_channel = replyChannel;
  data.researcher_contact = `<@${userId}>`;
  data.detected_files = documents.map(d => d.name).join('\n- ');
  data.stakeholder_count = documents.length;
  data.file_list = documents.map(d => d.name);
}
```

### 3b. YAML changes (`stakeholder_synthesis.yaml`)

**Split into 3 AI tasks:**

1. `stakeholder_table` — Generate the stakeholder ID/role mapping table from interview data. Input: combined_file_content. Output: markdown table with SH-001/role/team/focus.

2. `analysis_body` — Generate sections 01-05 plus 06-07 as continuous analytical prose. Input: combined_file_content + stakeholder table (from task 1... but tasks run in parallel, so task 2 can't receive task 1's output).

   **Problem:** yamlProcessor runs all AI tasks in parallel (`Promise.all`). Task 2 can't receive task 1's output. Two options:
   - (a) Keep stakeholder_table + analysis_body as one task (back to 2 tasks total)
   - (b) Pre-compute stakeholder table in the handler (like brief's barriers)

   **Recommendation: Option (a).** Combine stakeholder table + analysis body into one task. This gives us 2 AI tasks + Handlebars structure — a significant improvement over the current 1-task-does-everything pattern.

3. `appendix_observations` — Raw system/process observations, 3-5 entries. Separate from analysis because these are preservation, not synthesis.

**Restructure output template:**

Handlebars owns:
- Masthead
- Section headings (## 01 through ## 07)
- Methodology framework text
- Validity checklist table
- References list
- Appendix HTML structure (`<details>`/`<summary>`)
- Cascade summary (always present, not conditional on upstream)

AI fills bounded slots within each section.

**Remove `derived_variables` block.** Handler computes `topic_slug`.

### 3c. Cascade contract changes

None. All 6 emitted variable shapes stay the same. The `extract_from` hints reference section headings which move from LLM-generated to Handlebars-rendered — this improves extraction reliability since section names are now fixed strings.

### 3d. Update `extract_from` hints

The current hints reference section numbers ("## 01", "## 02", etc.). With Handlebars-rendered headings, these are guaranteed to be present and correctly formatted. No hint changes needed — the headings stay the same.

## 4. Cascade contract impact

### Downstream consumers

No changes needed. All 6 variables maintain their schemas:
- `stakeholder_constraints`: 10+ field object array (consumed by brief, readouts, design opportunities, service blueprint)
- `stakeholder_priorities`: object array (consumed by brief)
- `alignment_gaps`: object array (consumed by brief, readouts)
- `stakeholder_questions_for_users`: object array with priority enum (consumed by brief — drives research question generation)
- `backstage_observations`: object array (consumed by service blueprint)
- `system_failure_modes`: object array (consumed by service blueprint)

### Extraction impact

**Positive.** Section headings rendered mechanically (Handlebars) means the extractor always sees consistent section names. Currently the LLM occasionally varies heading format ("## 01 Constraints" vs "## 01 &nbsp;&nbsp; Constraints") which can affect extraction.

## 5. Risks

### Risk 1: Analysis coherence loss from task split

The monolithic task maintains cross-references: SH-001 appears in constraints, then in priorities, then in questions. Splitting into separate tasks could break this coherence.

**Mitigation:** Keep the main analytical content in one task (analysis_body). Only split out the stakeholder table and appendix observations. The core 7 sections stay in one analytical pass.

### Risk 2: Largest restructure so far — more surface area for regressions

The stakeholder synthesis template is 748 lines with complex formatting (mermaid diagrams, details/summary blocks, conditional cascade rendering, editorial numbering). More things can break during restructuring.

**Mitigation:** Test incrementally. Start with the structural split (Handlebars for static content) before touching the analytical task. Verify rendering after each step.

### Risk 3: Mermaid diagram syntax in Handlebars

The template generates Mermaid sequence diagrams inside code fences. Handlebars uses `{{` which could conflict with Mermaid syntax if the diagram template is in the Handlebars output template. However, since the diagrams are inside an AI task output (not in the Handlebars template), this is not an issue — the AI generates the diagrams and Handlebars renders the result as-is.

### Risk 4: Token budget improvement may not be as large as expected

Pulling ~60-80 lines of static content out of the LLM task should free token budget. But the analytical content is already dense. If the LLM was already within budget, the improvement is marginal. If it was truncating, the improvement is significant.

**Mitigation:** Monitor output completeness. If the methodology/appendix sections are truncated in the current version, the restructure fixes it. If they're not, the improvement is about rendering reliability, not token budget.

## 6. Implementation sequence

1. **Handlebars skeleton:** Build the output template with mechanical sections (masthead, headings, methodology, validity checklist, references, appendix structure, cascade summary). Leave AI slots as `{{ai_generated.X}}` placeholders.

2. **Split AI tasks:** Rewrite the monolithic prompt into 2-3 focused tasks. Each task receives the interview data and produces its section.

3. **Update cascade summary:** Always render (not conditional on upstream data). Document all 6 emitted variables.

4. **Remove dead YAML:** Delete `derived_variables` block. Update notes section.

5. **Test:** Typecheck, unit tests, manual generation with uploaded interview transcripts. Verify all 7 sections render, mermaid diagrams work, extraction produces same 6 variable types.

**Estimated effort:** 1-2 sessions (larger than desk research due to complexity).
