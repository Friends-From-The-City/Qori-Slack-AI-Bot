## 1. Current state of jobs_to_be_done

### Architecture

Single-LLM blob. One task `jtbd_complete` (~130 lines of prompt) generates the entire document including title, masthead, methodology, references, and footer. Output template: `{{ai_generated.jtbd_complete}}`. Handler routes through `researchSynthesisHandler.ts` via `ANALYSIS_YAML_MAPPING['jobs_to_be_done'] = 'jobs_to_be_done.yaml'`. Listed in `NUGGET_REQUIRED_METHODS`.

### Cascade contract -- consumes

| Variable | Source | Required | inject_as |
|----------|--------|----------|-----------|
| `atomic_nuggets` | session_summary | Yes | context |
| `validated_themes` | affinity_mapping | No | context |

2 upstream variables. Same pattern as usability_issues pre-restructure: generic `atomic_nuggets` key instead of split core+detail. `inject_as: context` instead of `reference`.

### Cascade contract -- emits

**None.** The template generates rich structured JTBD data (When/Want/So statements, functional/emotional/social dimensions, pain points with citations, design opportunities, priority matrix) but declares no `emits:` section.

### Downstream consumers expecting output

**None declared.** No template in `config/prompts/` references `jobs_to_be_done`, `validated_jobs`, `jtbd`, or `job_statement` in its consumes block. This is a pure cascade dead-end — unlike usability_issues which had a broken contract (research_readout expected the output), JTBD output goes nowhere.

### What the LLM generates that should be mechanical

| Element | Current | Should be |
|---------|---------|-----------|
| Document title + summary stat line | LLM generates `# 🎯 Jobs to be Done: {{selected_study}}` | Handlebars |
| At a Glance table | LLM generates | Keep in LLM -- analytical synthesis |
| Per-job sections (When/Want/So, dimensions, workarounds, pain points, design opportunity) | LLM generates | Keep in LLM -- core analysis |
| Priorities table | LLM generates | Keep in LLM -- analytical |
| Methodology + references | LLM generates static framework description + references | **Split:** Handlebars renders references (static), LLM writes data sources |
| Footer (`*Generated by Qori*`) | LLM generates | Handlebars (backend footer handles this) |
| Cascade summary | **Missing** | Handlebars (standard v7.0) |
| Upstream context | **Missing** | Handlebars (conditional on upstream vars) |
| Validity checklist | **Missing** | Handlebars (static) |

### Anti-fabrication guards

**Present but lighter than usability_issues.** 5 rules:

1. JOBS ARE PROGRESS, NOT TASKS -- domain-specific framing guard with test ("Can you describe the job WITHOUT mentioning the app?")
2. NO HALLUCINATION -- citations required
3. VA CONTEXT ONLY -- domain-scoped
4. JOBS MUST BE DISTINCT -- deduplication
5. BEFORE SUBMITTING, VERIFY -- quality checklist

Missing compared to usability_issues: no CITE EVERYTHING rule with nugget ID format, no systematic extraction order, no confidence assessment. The "progress not tasks" rule (#1) is JTBD-specific and strong.

### Known bugs

- **`{{focus_area}}`** referenced at line 98 but never provided by handler (documented in v3.5 notes as "latent bug, kept as-is"). Should be removed in v7.0.
- **Footer** `*Generated by Qori • {{current_date}}*` at line 183 renders inside LLM output; backend footer already handles this.

### Dead metadata sections

`processing_workflow`, `auto_variables`, `notify`, `quality_assurance` -- documentation-only, never read by backend. Safe to remove.

## 2. Emit schema design: validated_job

### Design rationale

JTBD output has no declared downstream consumer today, but the data has clear value for two templates:
- **design_opportunities**: Jobs define the "progress" that design opportunities should enable. Currently design_opportunities consumes nuggets + themes + personas but lacks the explicit "what users are trying to accomplish" framing that JTBD provides.
- **research_readout**: The readout's "Why we conducted this research" and findings sections could reference validated jobs as an additional analytical lens.

The schema should capture the Christensen When/Want/So structure plus the three-dimensional need model (functional/emotional/social) that the LLM already generates.

### Comparable schemas

| Schema | Purpose | Required fields | Nullable fields | Total |
|--------|---------|:-:|:-:|:-:|
| `prioritized_issue` | Severity-rated interface problem | 7 | 10 | 17 |
| `validated_theme` | Cross-participant pattern | 5 | 14 | 19 |
| `journey_pain_point` | Stage-specific friction | 3 | 5 | 8 |

`validated_job` should be moderate -- the When/Want/So statement is the required core, with dimensional needs and evidence as enrichment.

### Proposed schema: `validated_job.yaml`

```yaml
# Validated job -- progress-focused need extracted from research data
# Emitted by: jobs_to_be_done
# Consumed by: design_opportunity_generator (job framing), research_readout (analytical lens)
#
# Follows Christensen's JTBD framework: jobs describe the progress people
# want to make, not tasks they perform. Stable across technology changes.
type: object
required: [id, job_title, when_situation, want_motivation, so_outcome, evidence_nuggets, confidence]
properties:
  # -- Required core (7 fields) --
  id:
    type: string
    description: "Format: job-01, job-02, etc."
  job_title:
    type: string
    description: "Progress-focused name, not task-focused. Test: describable without mentioning the app"
  when_situation:
    type: string
    description: "The triggering situation: 'When I [specific context from research]'"
  want_motivation:
    type: string
    description: "The desired progress: 'I want to [progress, NOT a UI action]'"
  so_outcome:
    type: string
    description: "The life outcome: 'So I can [outcome, NOT app outcome]'"
  evidence_nuggets:
    type: array
    items:
      type: string
    description: "References to atomic_nugget_core.id values supporting this job"
  confidence:
    type: string
    enum: [Strong, Moderate, Limited]
    description: "Evidence quality assessment"

  # -- Enrichment (10 nullable fields) --
  job_type:
    type: string
    nullable: true
    enum: [functional, emotional, social, composite]
    description: "Primary dimension of the job"
  functional_need:
    type: string
    nullable: true
    description: "What they're trying to accomplish (task dimension)"
  emotional_need:
    type: string
    nullable: true
    description: "How they want to feel (affect dimension)"
  social_need:
    type: string
    nullable: true
    description: "How they want to be perceived (identity dimension)"
  current_workaround:
    type: string
    nullable: true
    description: "What they 'hire' to do this job today"
  participants_observed:
    type: array
    nullable: true
    items:
      type: string
    description: "PT-XXX IDs who expressed this job"
  participant_coverage:
    type: string
    nullable: true
    description: "X of Y participants format"
  linked_themes:
    type: array
    nullable: true
    items:
      type: string
    description: "validated_theme.id references if job maps to themes"
  linked_barriers:
    type: array
    nullable: true
    items:
      type: string
    description: "target_barrier IDs (TB-XXX) if job relates to a barrier"
  design_opportunity:
    type: string
    nullable: true
    description: "Specific implementable fix that addresses this job's pain points"
```

**Total: 7 required + 10 nullable = 17 fields.** Extraction model: Sonnet (When/Want/So synthesis + evidence linking requires reasoning). Replace strategy (study-level, not pooled).

### Schema design notes

The When/Want/So fields are split into three separate required fields rather than a single `job_statement` string. This enables downstream templates to reference specific parts: design_opportunities can key on `want_motivation`, research_readout can reference `when_situation` for context framing.

The three-dimensional need model (functional/emotional/social) maps directly to the LLM's per-job output table. These are nullable because not every job has all three dimensions clearly evidenced.

## 3. Downstream wiring

### New consumer: design_opportunity_generator

design_opportunities currently consumes nuggets + themes + personas + stakeholder_constraints but lacks explicit JTBD framing. Adding `validated_jobs` gives it the "what users are trying to accomplish" lens that makes HMW ("How Might We") statements more progress-focused.

**Proposed addition to design_opportunity_generator.yaml consumes:**
```yaml
- key: validated_jobs
  source: jobs_to_be_done
  required: false
  inject_as: reference
  description: "Progress-focused jobs for opportunity framing (what users are trying to accomplish)"
```

### Potential consumer: research_readout

research_readout already consumes 16+ upstream variables. Adding another optional reference adds marginal value vs. complexity. The readout's findings already incorporate themes and nuggets which capture the same behavioral patterns that JTBD formalizes differently.

**Decision: Defer.** Wire design_opportunities now. Research_readout can add JTBD consumption later if the readout's findings quality improves with job framing.

### Summary

| Consumer | Variable | Required | Action |
|----------|----------|----------|--------|
| design_opportunity_generator | `validated_jobs` | No | **Add** -- wires JTBD into opportunity framing |
| research_readout | -- | -- | **Defer** -- already has 16 upstream vars |

## 4. Target state

### v7.0 structural restructure

Same pattern as usability_issues v7.0: single `analysis_body` task + Handlebars for mechanical structure.

**Task split:**

1. `analysis_body` -- At a Glance table, per-job sections (When/Want/So statement, functional/emotional/social dimensions, current workarounds, pain points with evidence, design opportunity), Priorities table. USE `##` headings. Do not generate title, methodology framework description, references, upstream context, cascade summary, validity checklist, or footer.

2. Handlebars renders:
   - **Masthead:** `# Jobs to be Done` + study/researcher/date
   - **AI body:** `{{ai_generated.analysis_body}}`
   - **Methodology** (`<details>` toggle, static JTBD framework description + references)
   - **Upstream context** (`<details>` toggle, conditional on upstream vars)
   - **Validity checklist** (`<details>` toggle, static)
   - **Cascade summary** (standard v7.0 -- emits + consumes)

## 6. Risks

### Risk 1: First-time extraction for validated_jobs

Same risk as usability_issues. The schema has 7 required + 10 nullable fields across ~3-6 jobs per study. The When/Want/So fields require the LLM to separate a compound statement into three parts during extraction.

**Mitigation:** Sonnet extraction. The prompt already generates When/Want/So as separate blockquote lines, making extraction targets clear. The `extract_from` hint targets numbered job sections.

### Risk 2: No existing downstream consumer to verify

Unlike usability_issues (where research_readout already consumed the output), validated_jobs has no existing consumer to test against. We're adding the emit AND the consumer (design_opportunities) simultaneously.

**Mitigation:** Test in two steps: (1) verify extraction produces valid JSON, (2) run design_opportunities and confirm `upstream_validated_jobs` appears in the prompt context. The consumer addition is optional (required: false), so design_opportunities works with or without it.

### Risk 3: focus_area removal

The `{{focus_area}}` variable is referenced in the prompt but never provided. Removing it changes the rendered prompt slightly (the LLM currently sees `Focus Area:` with an empty value).

**Mitigation:** Removing a never-populated variable has zero functional impact. The LLM already ignores the empty field.
