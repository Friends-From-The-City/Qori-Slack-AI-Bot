## 1. Current state of usability_issues_extractor

### Architecture

Single-LLM blob. One task `usability_complete` (~240 lines of prompt) generates the entire document. Output template: `{{ai_generated.usability_complete}}`. Handler routes through `researchSynthesisHandler.ts` via `ANALYSIS_YAML_MAPPING['usability_issues'] = 'usability_issues_extractor.yaml'`. Listed in `NUGGET_REQUIRED_METHODS`, meaning the handler enforces upstream nugget availability.

### Cascade contract -- consumes

| Variable | Source | Required | inject_as |
|----------|--------|----------|-----------|
| `atomic_nuggets` | session_summary | Yes | context |
| `validated_themes` | affinity_mapping | No | context |

2 upstream variables. Note: consumes `atomic_nuggets` (generic key) rather than the split `atomic_nugget_core` + `atomic_nugget_detail` that v7.0 templates use. This should be updated to consume both core and detail separately, matching affinity_mapping's pattern.

### Cascade contract -- emits

**None.** This is the primary bug. The template generates a rich usability issues document with per-issue severity, evidence, fix recommendations, and priority rankings -- but declares no `emits:` section. All this structured data dies in the markdown file.

### Downstream consumers expecting output

| Consumer | Variable expected | Source declared | inject_as | Required |
|----------|------------------|-----------------|-----------|----------|
| `research_readout` | `prioritized_issues` | `usability_issues` | reference | No |

research_readout is the only direct consumer. It expects `prioritized_issues` as optional reference data for findings prioritization. The readout currently generates findings without this input (graceful degradation), but the findings would be stronger with issue-level severity and evidence pre-computed.

Indirect consumers (via research_readout's emits): designer_readout, engineering_readout, accessibility_readout, leadership_readout all consume `prioritized_findings` from research_readout, which itself would benefit from `prioritized_issues` input.

### What the LLM generates that should be mechanical

| Element | Current | Should be |
|---------|---------|-----------|
| Document title + summary stat line | LLM generates | Handlebars |
| At a Glance table | LLM generates | Keep in LLM -- analytical synthesis |
| Per-issue sections (problem, behavior, evidence, severity, fix) | LLM generates | Keep in LLM -- core analysis |
| What's Working table | LLM generates | Keep in LLM -- extraction |
| Cross-Issue Connections | LLM generates | Keep in LLM -- synthesis |
| Recommended Fix Priority table | LLM generates | Keep in LLM -- analytical |
| Methodology section | LLM generates | **Split:** Handlebars renders static framework description + references, LLM writes severity criteria |
| Footer (`*Generated by Qori*`) | LLM generates | Handlebars (backend footer handles this) |
| Cascade summary | **Missing** | Handlebars (standard v7.0) |
| Upstream context | **Missing** | Handlebars (conditional on upstream vars) |
| Validity checklist | **Missing** | Handlebars (static) |

### Anti-fabrication guards

**Present and strong.** 6 numbered rules:

1. NO HALLUCINATION -- extract only, every issue from actual observations, every quote verbatim
2. SYSTEMATIC EXTRACTION -- process data in defined order
3. VA GOVERNMENT CONTEXT -- domain-scoped
4. CITE EVERYTHING -- participant ID + timestamp
5. ISSUES MUST BE DISTINCT -- combine similar issues
6. SPECIFIC ISSUE NAMES -- no generic UX jargon

Quality checklist at prompt end (marked "DO NOT OUTPUT"). These are fieldwork-appropriate guards. Preserved as-is.

### Handler concerns

Routes through `researchSynthesisHandler.ts`. No handler changes needed for v7.0 restructure -- the handler calls `processYamlTemplate()` which reads the YAML. The handler does need to support the new `emits:` section, but this is automatic -- `yamlProcessor.ts` already handles emit extraction for any template that declares `emits:`.

### Dead metadata sections

`processing_workflow`, `notify`, `quality_assurance` -- documentation-only, never read by backend. Safe to remove.

## 2. Emit schema design: prioritized_issue

### Design rationale

research_readout consumes `prioritized_issues` with `inject_as: reference`. It uses these to enrich findings prioritization -- specifically, pre-computed severity ratings, evidence links, and fix patterns inform the readout's finding ordering and recommendation specificity.

The schema should capture what the LLM already generates in the per-issue sections: issue identity, severity with rationale, evidence links back to nuggets, affected participants, fix recommendation, and usability-specific classification.

### Comparable schemas

| Schema | Purpose | Required fields | Nullable fields | Total |
|--------|---------|:-:|:-:|:-:|
| `validated_theme` | Cross-participant pattern | 5 | 14 | 19 |
| `journey_pain_point` | Stage-specific friction | 3 | 5 | 8 |
| `prioritized_finding` | Readout-level insight | 4 | 13 | 17 |

`prioritized_issue` should be closer to `journey_pain_point` in required field count (lean core, rich enrichment) but with usability-specific fields like Nielsen severity, fix complexity, and task impact.

### Proposed schema: `prioritized_issue.yaml`

```yaml
# Prioritized usability issue -- severity-rated interface problem with evidence and fix
# Emitted by: usability_issues_extractor
# Consumed by: research_readout (findings prioritization)
#
# Design: Lean required core (7 fields) + rich enrichment (10 nullable).
# Required fields are what downstream templates need for prioritization.
# Enrichment fields provide context for deeper analysis.
type: object
required: [id, issue_title, category, severity, participants_affected, evidence_nuggets, confidence]
properties:
  # ── Required core (7 fields) ──────────────────────────────
  id:
    type: string
    description: "Format: issue-01, issue-02, etc."
  issue_title:
    type: string
    description: "Specific issue name from participant language, not generic UX jargon"
  category:
    type: string
    enum: [navigation, forms, search, content, visual_design, accessibility, feedback, workflow, error_handling]
    description: "Issue classification for downstream filtering"
  severity:
    type: integer
    description: "1-4 Nielsen scale: 1=cosmetic, 2=minor, 3=major, 4=catastrophic"
  participants_affected:
    type: array
    items:
      type: string
    description: "PT-XXX IDs who experienced this issue"
  evidence_nuggets:
    type: array
    items:
      type: string
    description: "References to atomic_nugget_core.id values documenting this issue"
  confidence:
    type: string
    enum: [Strong, Moderate, Limited]
    description: "Evidence quality assessment"

  # ── Enrichment (10 nullable fields) ────────────────────────
  issue_description:
    type: string
    nullable: true
    description: "1-2 sentence description of what's broken and why it matters"
  location:
    type: string
    nullable: true
    description: "Specific screen, feature, or interface element where issue occurs"
  frequency:
    type: string
    nullable: true
    enum: [all_users, majority, several, isolated]
    description: "How widely observed across participant pool"
  participant_coverage:
    type: string
    nullable: true
    description: "X of Y participants format, e.g. '4 of 6'"
  task_impact:
    type: string
    nullable: true
    description: "How this affects task completion (blocks, delays, workaround needed)"
  fix_recommendation:
    type: string
    nullable: true
    description: "Primary specific, actionable fix"
  fix_complexity:
    type: string
    nullable: true
    enum: [Low, Medium, High]
    description: "Implementation effort estimate"
  quick_win:
    type: boolean
    nullable: true
    description: "True if low-effort fix with high impact"
  linked_themes:
    type: array
    nullable: true
    items:
      type: string
    description: "validated_theme.id references if issue maps to a theme"
  linked_barriers:
    type: array
    nullable: true
    items:
      type: string
    description: "target_barrier IDs (TB-XXX) if issue validates a barrier"
```

**Total: 7 required + 10 nullable = 17 fields.** Extraction model: Sonnet (severity assessment + evidence linking requires reasoning).

### Schema comparison

| Field | prioritized_issue | validated_theme | journey_pain_point |
|-------|:-:|:-:|:-:|
| id | req | req | req |
| title/name | req (issue_title) | req (theme_name) | req (pain_point) |
| category | req | -- | -- |
| severity (integer) | req | -- | nullable |
| confidence | req | req | -- |
| evidence_nuggets | req | req (supporting_nuggets) | nullable |
| participants | req | nullable | nullable |
| description | nullable | req (summary) | -- |
| location/stage | nullable | -- | req (stage_id) |
| frequency | nullable | -- | -- |
| fix_recommendation | nullable | -- | nullable (intervention_opportunity) |
| fix_complexity | nullable | -- | -- |
| linked_barriers | nullable | nullable | nullable |
| linked_themes | nullable | -- | -- |

The `prioritized_issue` schema is issue-scoped (specific interface problem) vs. theme-scoped (cross-participant pattern). The key differentiator is the fix fields (recommendation, complexity, quick_win) which validated_theme doesn't have -- themes describe patterns, issues describe actionable problems.

## 3. Downstream wiring

### Direct consumer: research_readout

Already declared. research_readout consumes `prioritized_issues` from `usability_issues` (optional, reference). When present, the readout uses severity ratings to inform finding prioritization and fix complexity to inform recommendation feasibility. **No changes needed to research_readout's cascade contract.**

### Potential new consumers

| Template | Would consume | Benefit | Recommendation |
|----------|--------------|---------|----------------|
| designer_readout | `prioritized_issues` | Pre-computed fix recommendations + severity for design ticket generation | **Defer.** Designer readout already gets this through research_readout's `prioritized_findings`. Adding direct consumption creates a dual-path that complicates the cascade without clear value. |
| engineering_readout | `prioritized_issues` | Technical location + fix complexity for engineering ticket scoping | **Defer.** Same reasoning -- engineering readout consumes research_readout findings which incorporate issue data. |
| accessibility_readout | `prioritized_issues` (filtered for category=accessibility) | Direct accessibility issue pipeline | **Defer.** Accessibility readout already filters nuggets by `nugget_type=accessibility_issue`. Adding issue-level filtering creates redundancy. |

**Decision: No new downstream wiring.** research_readout is the sole consumer. The readout layer already distributes findings to audience-specific templates. Adding direct consumption from synthesis-layer templates to audience-layer templates would bypass the readout aggregation step and create maintenance burden.

## 4. Target state

### v7.0 structural restructure

Same pattern as affinity_mapping/persona_generator: single `analysis_body` task + Handlebars for mechanical structure.

**Task split:**

1. `analysis_body` -- At a Glance table, per-issue sections (problem, behavior/expectation analysis, evidence table, severity assessment, fix recommendations), What's Working, Cross-Issue Connections, Recommended Fix Priority table. USE `##` headings. Do not generate title, methodology framework description, references, upstream context, cascade summary, validity checklist, or footer.

2. Handlebars renders:
   - **Masthead:** `# Usability Issues Report` + study/researcher/date
   - **AI body:** `{{ai_generated.analysis_body}}`
   - **Methodology** (`<details>` toggle, static framework description)
   - **Upstream context** (`<details>` toggle, conditional on upstream vars)
   - **Validity checklist** (`<details>` toggle, static)
   - **Cascade summary** (standard v7.0 -- emits + consumes)

### Cascade contract updates

**Consumes (updated):**

| Variable | Source | Required | inject_as | Change |
|----------|--------|----------|-----------|--------|
| `atomic_nugget_core` | session_summary | Yes | reference | **Renamed** from `atomic_nuggets` |
| `atomic_nugget_detail` | session_summary | Yes | reference | **New** -- split consumption |
| `validated_themes` | affinity_mapping | No | reference | **inject_as changed** from context to reference |
| `target_barriers` | research_brief | No | grounding | **New** -- enables TB-XXX citation |
| `research_questions` | research_brief | No | context | **New** -- enables RQ-XXX citation |

**Emits (new):**

| Variable | Pool | Strategy | Schema | Extract from |
|----------|------|----------|--------|-------------|
| `prioritized_issues` | No | replace | `schemas/prioritized_issue.yaml` (array) | All numbered issue sections |

### Cascade-aware generation

When upstream brief variables exist, the prompt includes instructions for:
- [TB-XXX] citation markers when issues validate target barriers
- [RQ-XXX] citation markers when issues address research questions
- Category filtering based on upstream methodology context

## 6. Risks

### Risk 1: Extraction reliability for new emit (first-time extraction)

This is the first time `prioritized_issues` will be extracted. The schema has 7 required + 10 nullable fields across ~3-8 issues per study. Extraction complexity is moderate (comparable to validated_themes at 5 req + 14 nullable across ~3-7 themes).

**Mitigation:** Sonnet extraction model. The prompt already generates per-issue structured content (severity, evidence, fix) that maps cleanly to schema fields. The `extract_from` hint targets numbered issue sections. Post-extraction validation checks required field presence.

### Risk 2: Consumes key rename (atomic_nuggets -> split)

Renaming `atomic_nuggets` to `atomic_nugget_core` + `atomic_nugget_detail` changes how the yamlProcessor injects upstream data. If the processor handles the old generic key differently, the rename could break injection.

**Mitigation:** All other v7.0 templates (affinity_mapping, persona_generator, journey_mapping) use the split pattern successfully. The yamlProcessor resolves consumes by key name from the study variables store. The store has `atomic_nugget_core` and `atomic_nugget_detail` as separate entries. The old `atomic_nuggets` key may not exist in the store at all (it was likely a documentation-level alias).

### Risk 3: research_readout graceful degradation

research_readout declares `prioritized_issues` as optional. Currently it generates findings without this input. After the emit is wired, the readout will receive issue data and may change its output. This is the intended behavior but should be verified.

**Mitigation:** Run research_readout with and without `prioritized_issues` after implementation. The readout's prompt handles optional upstream data conditionally (`{% if upstream_prioritized_issues %}`).

### Risk 4: Schema evolution

The `prioritized_issue` schema is new. If the shape doesn't match what research_readout expects (the readout was written before the schema existed), the readout's prompt may not reference the fields effectively.

**Mitigation:** Review research_readout's prompt for how it uses `upstream_prioritized_issues`. The readout injects it as reference data -- the LLM reads the JSON and uses what's relevant. The schema is designed to match the readout's stated purpose ("severity-rated issues for findings prioritization").
