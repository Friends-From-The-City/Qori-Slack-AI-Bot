### Key structural changes

1. **4 AI tasks → 1 comprehensive task** — Current v3.3 splits into 4 tasks to avoid truncation. With `max_tokens: 8192` and a leaner output (~290 lines vs ~486 lines), single-task consolidation produces more coherent synthesis. Same pattern as persona_generator v4.3 and discussion_guide v6.2.
2. **Section count: 12 sections → 7 numbered sections + Methodology + Appendix** — Significant reduction in surface area.
3. **Sequence diagrams: unlimited → maximum 2** — Current v3.3 generates diagrams for every process mentioned. Locked design picks the 2 flows that surface invisible failure modes text alone cannot convey.
4. **Constraint triangulation preserved** — The Type column in the single constraints table still shows which role surfaced each constraint. Multi-stakeholder constraints show multiple sources.
5. **Approval section: none** — Stakeholder synthesis is a findings document, not an approval gate. No approval checklist.

## Section B: Pattern A modified application

Stakeholder synthesis uses **Pattern A modified** — the same variant as persona_generator v4.3.

### What "Pattern A modified" means for this template

| Aspect | Standard Pattern A (research readout) | Pattern A modified (stakeholder synthesis) |
|--------|---------------------------------------|-------------------------------------------|
| **Confidence** | Per finding — measures evidence strength | Per section — measures confidence that synthesis represents reality (not just that stakeholders said it) |
| **Sources lines** | Per finding — middle-dot-separated links to source docs | Not used — citations are inline via SH-XXX role-attribution at quotes |
| **Attribution** | PT-### participant IDs | SH-### role IDs (diplomatic for document read by the people interviewed) |
| **Detected files** | Used for Sources lines and Related Artifacts | Used for Related Artifacts only (Appendix) |
| **Methodology Sources** | Per-finding + consolidated in Methodology | Single "Sources analyzed" line in Methodology only |

### Confidence rubric for stakeholder synthesis

Different from user research confidence — this measures confidence in **interpretation**, not just evidence strength:

| Level | When to assign | Example |
|-------|---------------|---------|
| **Strong** | Multiple stakeholders independently surfaced the same claim AND claim is verifiable against external evidence (codebase, metrics, policy) | "Strong (multiple stakeholders independently surfaced constraints; technical claims verifiable against codebase)" |
| **Moderate** | Single stakeholder source OR partial triangulation OR claim plausible but not independently verified | "Moderate (process described by SH-003; SH-001 acknowledged the pattern but offered no countervailing evidence)" |
| **Limited** | Unverified stakeholder claim, single perspective, or inference required from limited context | "Limited (single stakeholder perspective, claim not verified against other sources)" |

## Section C: Critical anonymization rule

```
============================================================
CRITICAL RULE: ROLE-ONLY ATTRIBUTION
============================================================

Stakeholder synthesis uses role-only attribution. NEVER use real names from
stakeholder transcripts. Map each stakeholder to a role identifier:

- SH-001 = Role/title (e.g., "Product Owner")
- SH-002 = Role/title (e.g., "Engineering Lead")
- SH-003 = Role/title (e.g., "Accessibility Specialist")

Quote attribution format:
> "quote text"
> — SH-XXX

If a stakeholder's role would identify them within their organization
(e.g., only one Director of X exists), use a more generic role label.

The "Stakeholders interviewed" table is the ONLY place where role-to-ID
mapping appears. Never use real names anywhere in the document.
```

This rule must appear as the FIRST rule in the CRITICAL RULES block, before any other instructions. It is the most consequential rule in this template — violation produces a document that cannot be shared.

## Section D: Inputs and rationale

### Required inputs
- **Stakeholder interview transcripts** (multiple) — primary source. These are the raw transcripts or notes from internal stakeholder interviews. Passed as `combined_file_content` by the synthesis handler.

### Recommended inputs
- **Research plan** — provides study context (which product, what stakeholder ecosystem). Not currently auto-injected by the handler, but if selected files include it, the LLM can use it for grounding.
- **Stakeholder interview guide** — informs what topics were covered, useful for identifying gaps in coverage.

### Excluded inputs
- **Session summaries** (user research sessions, PT-### participants) — different research stream. Stakeholder synthesis is about internal stakeholders, not end users.
- **User-research synthesis files** (affinity map, personas, journey map, etc.) — different analytical layer. Stakeholder synthesis happens in parallel or before user research.
- **Coded transcripts** — no longer in the flow (removed from pipeline).

## Section G: Flagged decisions

### Decision 1: System observations Appendix — preserve or cut?

**Recommendation: Preserve in `<details>` block.**

**Trade-off:** Redundancy (observations are in transcripts) vs. always-available context (service blueprint doesn't need to re-extract from full transcripts).

**Argument for preserving:** The stakeholder synthesis already did the work of identifying system-relevant observations. The service blueprint template can reference these directly instead of re-processing full transcripts. The `<details>` block keeps it collapsed by default — zero visual noise for readers who don't need it.

**Argument for cutting:** The raw transcripts are available. Adding an Appendix section increases output length and LLM token usage. The service blueprint handler could just re-read the transcripts.

**My recommendation:** Preserve. The observations are curated (3-5 items, not the full transcript) and formatted with system flow descriptions that the service blueprint needs. Re-extracting from full transcripts is wasteful and may produce different extractions. The LLM instruction should be: "Extract 3-5 system or process observations from the interviews. Preserve the stakeholder's description of how the system works. Include direct quotes. Do not synthesize or draw conclusions — these are raw inputs for downstream service blueprint synthesis."

**Awaiting your call.**

### Decision 2: "Most actionable insight" content — what should the LLM identify?

**Recommendation: Identify the diagnostic disagreement or alignment gap.**

The locked reference shows: *"Stakeholders agree navigation is broken, but disagree on root cause — Product frames it as IA, Engineering as performance, Accessibility as focus management."*

This is the sharpest kind of insight: everyone agrees there's a problem, but they diagnose it differently, which means the technical fix differs by diagnosis. User research resolves the disagreement.

**Instruction:** "Identify the most consequential cross-stakeholder pattern. Prioritize: (1) diagnostic disagreements — stakeholders agree on the problem but disagree on the cause; (2) alignment gaps — stated priorities vs. actual behavior; (3) invisible dependencies — where one team's decision blocks another team's work. If none of these apply, identify the single finding with the highest organizational leverage."

**Awaiting your call.**

### Decision 3: Confidence rubric — use the proposed three-tier or different?

**Proposed rubric:**

| Level | Criteria |
|-------|---------|
| **Strong** | Multiple stakeholders independently surfaced the same claim AND claim is verifiable against external evidence |
| **Moderate** | Single stakeholder source OR partial triangulation OR claim plausible but not independently verified |
| **Limited** | Unverified stakeholder claim, single perspective, or inference required |

**Key difference from user research:** User research confidence measures *evidence strength* (how many data points, how consistent). Stakeholder synthesis confidence measures *interpretation accuracy* — how confident are we that what stakeholders told us reflects reality? Stakeholders have agendas, blind spots, and organizational incentives. A claim repeated by three stakeholders could still be wrong if they share the same blind spot.

The rubric above handles this by requiring external verification for "Strong" — stakeholder agreement alone is necessary but not sufficient.

**Awaiting your call.**

### Decision 4: Strategic priorities "Aligns with user need?" column — LLM judgment criteria

**Proposed instruction:**

```
For the "Aligns with user need?" column, apply these criteria:
- ✓ (check) — Priority directly addresses a user-facing problem or improves
  user task completion (e.g., "navigation overhaul" directly helps users)
- ⚠ (warning) — Priority is internal/technical with unclear or indirect user
  benefit (e.g., "framework upgrade" may improve performance but user impact
  is speculative)
- ✗ (cross) — Priority potentially conflicts with user needs or diverts
  resources from user-facing work (rare — only use when evidence supports)

Default to ⚠ when uncertain. The column's value is surfacing the
question, not answering it definitively.
```

**The "default to ⚠ when uncertain" instruction is important** — it prevents the LLM from confidently marking ✓ on everything, which would make the column useless.

**Awaiting your call.**

### Decision 5: Sequence diagram selection — how does the LLM pick the right 2?

**Proposed instruction:**

```
SEQUENCE DIAGRAM SELECTION (maximum 2):

Generate AT MOST 2 Mermaid sequence diagrams. Choose flows where:
1. The diagram reveals failure modes that text description alone cannot
   convey (invisible system hops, cascading failures, timing dependencies)
2. Multiple stakeholders described the same flow from different angles
3. The flow has quantifiable failure points (drop-off rates, latency,
   error frequencies)

DO NOT diagram:
- Working flows that can be described in prose
- Flows mentioned by only one stakeholder with no failure points
- Organizational processes (those belong in the Appendix observations)

If only one flow meets the criteria, generate only one diagram.
If no flows meet the criteria, skip diagrams entirely and note why
in a single sentence.
```

**Rationale:** The current v3.3 generates unlimited diagrams and suffers from truncation (Rule 5 in current prompt tries to mitigate but doesn't solve). Capping at 2 forces the LLM to choose the highest-value flows. The selection criteria ensure diagrams earn their space.

**Awaiting your call.**
